## 1. 为什么补充与如何计进度

R00—R14 已有审阅产物，旧 ID 28/28 已裁定，保留 3 条新增确认发现与 1 条 PENDING 候选。包状态不自动证明统一交付合同逐项满足。2026-09-30 完成情况核验发现以下收尾项，S00 执行时须重新检查并记录实际结果：

| 收尾项 | 已知观察 | 后续处理边界 |
|---|---|---|
| 必交文件 | R00 有 baseline.json，缺 baseline.md；R14 有 CURRENT_FINDINGS.json，缺统一合同要求的 findings.json | 补齐或形成明确、可机器读取的等价交付映射；不能仅改计划要求来掩盖缺口 |
| 动态验证枚举 | R06/R12/R13 合计 6 条 verification 使用合同外值 | 根据原证据归类，不把 S/H 标签误记为本轮动态成功；保留旧值及变更理由 |
| 覆盖状态 | R07 的 HISTORICAL_ONLY、NOT_REVIEWED 不在 coverage.review_status 允许集合 | 映射为 REVIEWED/PENDING/NOT_APPLICABLE，并保留证据层次和未覆盖原因 |
| 证据位置 | B12 的 fileAccessPolicy 路径拼写错误；D01 引用 verify-backup.py 的结束行超过实际 21 行 | 定向确认正确锚点，不改冻结脚本 |
| 修复卡完整性 | C01—C08 未逐卡齐备可改文件、停止条件、实施结果格式等字段 | 只完善设计交付，不实施修复；逐卡按原合同验收 |
| 状态与引用一致性 | 原 state 中 R09 缺起止 HEAD；新 ID 有 R06-N01/R12-N01 等历史写法 | 从现有证据补登记，缺证则明确未知；保留旧 ID 与别名映射，禁止静默改号 |

原计划允许继承足够的历史证据，允许明确 pending 收尾。没有浏览器、Linux 或全量重跑本身不自动构成违约；补证只用于解决尚不足以裁定的问题或界定影响范围。已经支持的缺陷仍保留原裁定，新增证据可支持修订但不自动表示修复。

后续报告分别列：①原轮包执行 15/15；②S00 交付规范逐项结果；③补充包完成数/7；④开放决策、环境阻碍、未执行实验数量；⑤缺陷裁定。不得将多个口径压成一个“100%”。

## 2. 执行边界与统一交付

- 旧目录 `docs/audits/2026-09-29-rdpms/` 及 manifest 冻结。开始补充包时核对 HEAD/工作树；有源码变化只登记和审查影响本包的增量。
- S00 可在正式执行时纠正 2026-09-30 执行产物，但必须先保存受影响文件的原内容及摘要，形成变更记录，更新受影响的派生台账和摘要；不可重新计算旧 manifest 来掩盖差异。本次规划不执行这些纠正。
- S01—S05 只写 `execution/supplemental/Sxx/`，通过追加裁定引用原发现。S06 才统一整合补充结论，保留原轮结果可追溯。
- 单包使用已有报告后再按调用边读源码；直接依赖超过 5 个额外文件先拆有边界子项，不扩为全仓重扫。
- 动态补证前先记录：要解决的唯一问题、静态证据为何不足、最小场景、隔离目录/数据库/浏览器所有权、预期信号、清理方式。禁止读取真实 .env、复用旧固定夹具库、对生产业务数据做实验。
- 未来运行环境不可得时记录 PLANNED_NOT_RUN 和解除条件；可继续本包独立静态审阅。没有环境时不得填动态成功。
- 不实施业务修复、依赖升级、数据清洗、生产迁移、部署或提交。应用改造与真正的修复验收仍属后续实施任务。

每个 S 包必交 `review.md`、`findings.json`（无结论变更可为空数组并解释）、`coverage.csv`、`open-items.json`。有实际实验才增加 `evidence/`，保存命令、夹具、退出码、日志、结果和清理记录。覆盖 CSV 继续使用原 7 列与合法状态。发现沿用原 ID；真正独立的新根因用 `N-Sxx-01`，不得重复计数。

开放项字段至少包含：id、关联 R 包/发现、问题、类型（ARTIFACT/STATIC_REVIEW/DECISION/ENVIRONMENT/EXPERIMENT）、当前证据、缺失输入、负责角色、解除条件、状态（OPEN/RESOLVED/DEFERRED）、理由。DEFERRED 不等于通过；不能擅自把必须审阅事项移交实施来宣称完成。

`SUPPLEMENTAL_STATE.json` 是补充包唯一状态入口，初始全为 NOT_STARTED。执行时仅主执行者更新包状态、实际起止 HEAD、产物、开放项、下一就绪包，并同步 `execution/handoff.md`。原 `execution/state.json` 继续描述 R00—R14。

## 4. 逐包任务卡

### S00：交付合同收尾

输入：REVIEW_PLAN 的统一合同、state/handoff、各包 JSON/CSV、R14 设计产物。主检查对象为审计文件，不重审业务处理器。

1. 为原任务卡各必交项建立交付映射，标出缺文件、等价内容和真正缺内容；核对上表全部已知缺口。
2. 为拟改文件保存原文/摘要与变更理由，再纠正格式、路径、行号；动态枚举依据证据性质调整。`SOURCE_ONLY` 等信息留在 evidence/limitation，不冒充动态运行。
3. R00 补足人可读基线入口；R14 明确逐条 findings 与聚合 CURRENT_FINDINGS 的生成关系，保证 28 个旧 ID 不丢失、不重复。
4. 按原合同逐卡补设计字段，尤其可改文件、停止条件和实施结果格式。这里只补卡片，不编辑实现代码。
5. 检查 state 起止 HEAD、输出列表、ID 别名、派生报告和输入摘要一致性；缺少执行时记录不得用本次 HEAD 伪造旧起点。

额外交付：`contract-checklist.csv`、`changes.json`（before/after 摘要、理由、证据）、`before/` 原文留存。退出条件：每项合同 PASS 或有具体未通过项；冻结目录摘要未变；28/28 ID 映射；无未解释的状态枚举/无效源码锚点；C01—C08 字段齐全。只完成扫描而未纠正，不能标 S00 COMPLETE。

### S01：规则依据与需要裁定的问题

输入：R01/R02/R04/R06/R09/R11 的 pending；已有 RBAC 签署规则、产品说明和相关任务卡。只沿已列规则查资料。

逐项核对：账号同级/更高等级重置与停用、custom role 绑定、强制改密会话权限、改密后 access token 失效时限、registration 全局查看/写范围、managerId 与成员角色关系、汇报复提来源状态、父任务/phase 软删与依赖 DAG 要求。

区分“已有书面依据”“源码当前行为”“需要业务选择”。没有规则证据时提出可执行选项、影响范围、需要批准的角色；不把代码现状自动当业务要求。重点复核 N-R02-02 的行为事实与缺陷定性是否需要政策支持，保留原结论并追加理由，不预设升级或降级。

额外交付：`decisions.md`、`decision-register.json`，每项关联发现、依据、备选、影响、责任角色及裁定状态。退出条件：所有上述问题有证据或明确决策请求。尚未得到业务答案可 COMPLETE_WITH_PENDING，不能宣称规则已经批准。

### S02：浏览器离线生命周期补证

输入：R07/R08/R02。目标入口为 AuthProvider、SyncProvider、engine/idb、tokenStore/http 和已定位缓存消费者。

1. 列启动恢复、显式退出、快速切号、两个标签页刷新、离线回退、IDB 升级的确定事件顺序；先核对已有 sessionGen、single-flight、deadLetter 原子移动等保护。
2. F01 仅在真实启动时序仍影响裁定时，用临时浏览器配置和合成账号预置归属 outbox，控制 /me 响应时机，观察最后可恢复副本。
3. F03 先确认真实页面消费者及字段授权，再设计 A/B 共享项目缓存场景；没有消费者不得宣称报告正文 UI 泄露。
4. F02 的浏览器 IDB 故障点、旧 schema 迁移中断、501+ 队列和 body byte 上限列最小场景；已有引擎证明足够的部分只继承，真实环境参数未知则列缺口。
5. N-R02-01 用受控双标签响应次序判断旧失败响应是否清除新 token；浏览器 context 必须明确共享同一 origin/storage，不能用隔离存储 context 代替双 tab。

额外交付：事件时间线与持久副本表。退出条件：每个场景的实际运行/不运行理由、证据层级、数据归属与影响边界齐备；没有运行的 UI/浏览器结论维持 pending。严禁为了复现删除用户真实浏览器数据。

### S03：同步协议与并发语义补审

输入：R05/R06/R09/R02，沿 sync 路由、相关命令、receipt 和实际 DTO 调用边定向读取。

1. 给拉取上下界、排序、分页、tombstone、提交可见顺序画时间线，区分 B07 已证截断与尚未证实的迟提交遗漏；不得假设自增序号天然等于提交顺序。
2. 核对新授权回填与撤权清理、成员角色 revision、项目/阶段/任务状态规则覆盖；HTTP 与 sync 的负责人转移、删除基线、敏感字段写入分别列对照。
3. 核对同 key 并发、回执保留/清理、批次中断及 HTTP 500 后客户端恢复；已有 B06 task 故障证据足够时不逐实体机械重跑。
4. 补查任务前端 revision 到 HTTP DTO 到命令参数的实际链路；汇报 submit 的版本分配、来源状态与快照一致性只针对现有未决点。
5. 对必须依赖数据库语义的一个疑点先设计事务屏障/确定调度，再在拥有的临时库运行；不使用随机 sleep 证明并发必然性。现有 access JWT 行为可静态确认，政策定性衔接 S01。

额外交付：`protocol-questions.md`、跨入口语义矩阵、必要场景的受控交错日志。退出条件：每个原 pending 被回答、保留有解除条件的 pending、或有明确理由延期；不预先选定 CDC/消息队列架构，不将不同场景重复编号。

### S04：模型约束与迁移片段

输入：R11、R03/R05/R06/R09 引用；仅检索 Task、ProjectPhase、ProjectMember、TaskDependency、相关软删/FK/索引的 migration 片段。

1. 对照当前 schema、初始迁移、之后修改上述对象的迁移，形成约束演化表；无需逐读无关表的整个迁移历史。
2. 核对同项目 parent/phase、任意长度环、软删关联、递归 projectId 过滤的应用与数据库职责；B19 维持“可建立异常边”的已证边界。
3. 设计只读异常关系统计查询和脱敏输出口径；只有明确归属的合成数据库可用于查询语义实验。没有获准业务数据源时只交查询方案，不报告真实异常数量。
4. 对 proposed 复合约束给出历史异常处理选项和上线前锁/兼容检查项，不运行迁移、不修历史数据、不凭无查询计划声称性能问题。

额外交付：`constraint-history.md`、只读数据核查方案。退出条件：相关迁移片段均有覆盖/缺失说明，规则归 S01，数据分布/锁耗时等尚未取得的信息明确保留。

### S05：备份恢复和发布证据

输入：R12/R13、相关脚本与非敏感运维说明。需要的外部材料：目标 Linux/文件系统和 cp/rsync 版本、备份窗口写入协调方式、脱敏有效配置、人工回滚 runbook、候选构建/迁移标识。

1. D01 只在临时目录补目标 Linux 的两轮新增/修改/删除语义，比较首快照字节/摘要；不能把 macOS 历史结果直接外推为生产损坏。
2. R12-N01 先确认脚本外是否有写入屏障或存储快照，再决定最小合成 DB+文件配对恢复实验是否必要；缺材料维持 PENDING。
3. B13 延用已有重复键计数证据，审阅逐表 unique/复合键/FK 与恢复结果合同；只有新增关键语义不足才补最小隔离场景。
4. D02/D03 用候选/当前目录和无敏感配置验证门禁目标与变量消费一致性，实际需要环境执行时使用临时副本；不读取真实 .env。
5. 人工回滚本身不计漏洞；核对已有非敏感 runbook、迁移向后兼容证据、build ID 和失败状态。真正服务切换或恢复演练须有明确可用的隔离主机/实例，本计划不授权在生产执行。

额外交付：`environment-requirements.md`、恢复点/失败状态矩阵、运行时才生成 manifest 和日志。退出条件：Linux/环境已证范围明确；缺配置/主机/规则的项带解除条件；R12-N01 有证据裁定或明确 pending；禁止无证据写生产验收通过。

## 5. 接续指令

先读本计划、SUPPLEMENTAL_STATE.json、execution/handoff.md。首次只执行 S00；用户要求连续执行时逐包保存检查点，随后选择依赖就绪包。S01—S05 可以并行，遇到明确阻碍只记录该项并推进独立工作。S06 最后汇总。

结束回报：原轮进度 → 本补充包状态/合同结果 → 发现裁定变化 → 已运行与未运行证据 → 开放项/解除条件 → 产物 → 下一就绪包。当前请求仅为更新计划，因此本文件中的纠正、审阅与实验全部留待执行阶段。
