## 发现与修复要求

下面源码位置均以导出包 `source/rdpms-system/` 为根，行号对应此次收到的版本。

### A01 / P1：历史版本接口缺少项目访问授权

- 位置：`backend/src/routes/reports.js:444`。
- 正文详情接口会检查项目访问；`GET /api/reports/:id/versions` 只检查全局 `reports.view`，直接查询版本正文。
- 独立复现 Q9：同一非成员身份，详情请求 404，历史版本请求 200，返回一条其他项目的合成正文。
- 证据等级：真实 Hono 应用路由，身份和数据库采用包内测试替身；未访问真实数据。
- 修复：版本读取先解析所属日报及项目，应用与详情一致的访问策略及删除状态处理。不要让版本 ID、日报 ID 成为绕过入口。
- 验收：非成员、被移出项目者、已删除资源的版本访问均符合既定隐藏策略；合法成员读取正常。补真实隔离数据库用例。

### A02 / P1：“创建日报”的 upsert 可绕过更新权限和并发基线

- 位置：`backend/src/routes/reports.js:132`、`:165`、`:176`。
- POST 按“项目＋作者＋类型＋周期”命中已有草稿后直接覆盖 content；只要求 `reports.create`，没有执行 PUT 的更新权限和基线保护。客户端声明 v2 也不改变这条路径。
- 独立复现 Q5：预置实验草稿 Ct=35，身份仅有 `reports.create`，不传基线，POST 同周期内容 Ct=20，响应 201；仍是一条记录，但实验内容已被覆盖。
- 这不是“是否重复创建”的问题，而是更新策略存在替代入口。PUT 的 U21 通过不能证明所有入口保护成立。
- 修复：明确区分创建与已有记录更新。已有记录要么拒绝创建请求并引导显式更新，要么转入同一更新命令，执行更新权限、状态和原子并发校验。校验使用事务内当前资源，不依赖事务外旧快照。保留已成功同 key 请求的授权后回放。
- 验收：仅 create 无 update 不能覆盖；v2 缺基线不能覆盖已有记录；科学草稿无基线不能覆盖；不同 key、相同基线的竞争写只能一方成功；原 key 重试不重复审计或修改。

### A03 / P1：旧同步响应可把 A 的草稿归到 B 名下

- 位置：`frontend/src/offline/engine.ts:185`、`:243`、`:337`、`:372`。
- 同步发出后未捕获不可变的用户/会话代次；处理拒绝结果时读取可变全局 `currentUserId`。stop() 不使在途请求失效。
- 独立复现 Q7：A 发出同步，暂停响应；退出 A，登录 B；释放 A 的拒绝响应。持久拒绝区中出现 `user-B:A-change`，payload 为 A 的合成草稿。
- 证据等级：原 engine/idb/deadLetter 源码，fake-indexeddb 和可控网络替身；不是完整浏览器证据，但串号路径已执行。
- 修复：每轮同步绑定 userId 和会话代次；所有异步回包及本地落盘都校验仍属于有效会话。账号切换使旧任务失效；本地事务必须写入原主体命名空间，不能通过当前用户变量重新归属。不能只在 UI 过滤已错误标成 B 的数据。
- 验收：延迟 A 的拉取和上行响应，切 B 后释放；B 的 records/outbox/deadLetters/conflicts/cursor 均不受 A 响应污染。

### A04 / P1：多项目与保存/提交复用的 key 管理器会重置历史 key

- 位置：`frontend/src/shared/idempotency.ts:38`；调用点 `frontend/src/pages/ReportEdit.tsx:339`、`:360`。
- 管理器只保存一个全局 fingerprint；任意 fingerprint 改变便清空整个 Map。实际不同项目 content 不同，保存与提交的 op 也不同。
- Q1：首次 A=key-1、B=key-2；重试 A=key-3、B=key-4。
- Q2：保存→提交→重试保存→重试提交，提交 key 从 key-6 变成 key-8。
- 现有 FE4 对所有项目传相同 fingerprint，未覆盖页面实际调用方式；FE6 只检查两类 key 不同，没有检查回来重试还能复用。
- 修复：用明确逻辑操作上下文，按命令＋资源分步骤保存 key、请求快照和成功状态。失败重试保留原 payload（包含基线）及 key；成功子步骤不重新当作新写入。整个操作完成或用户明确开始新操作才结束旧上下文。服务端 payloadHash 校验不得削弱。
- 验收：真实不同项目内容下 A 成功/B 失败/重试；保存成功、提交成功但响应丢失/重试；既检查 key，也检查版本和业务审计增量。

### A05 / P1：混合“有关联项目/无关联项目”的实验记录被静默丢弃

- 位置：`frontend/src/pages/ReportEdit.tsx:310`、`:321`。
- 只有所有记录都没有项目时才提示。混合情况下，无项目组被 `continue` 跳过，有项目组成功后清 key 并离开页面；被跳过内容没有失败项或持久保留步骤。
- 证据等级：静态控制流核查，尚未做浏览器复现。与 v2 目标架构第 4 节明确要求冲突。
- 修复：保存前逐条列出缺项目记录并保留；可以整体阻止提交，或明确显示未保存部分并持久留存，不能显示全部成功后丢失条目。
- 验收：一条有关联项目、一条无项目，保存/刷新/补关联后，原正文都可找回且各保存一次。

### A06 / P1：退出清理键名错误，冲突和游标残留

- 位置：`frontend/src/offline/idb.ts:169`；真实键定义在 `frontend/src/offline/engine.ts:25`。
- clearAll 删除的是 `cursor`、`acl`；使用的是 `rdpms.sync.cursor`、`rdpms.sync.acl`、`rdpms.sync.conflicts`，最后一个完全未清理。
- 独立复现 Q6：执行实际 clearAll 后，这三个真实键仍存在。新会话 hydrate 会继续读取共享冲突键。
- 修复：统一键定义及主体命名空间，账号切换不继承旧权限、游标或冲突；同时不要通过无提示清空未同步 outbox 来“解决隔离”。未提交内容需按既定策略保存或由用户显式处理。
- 验收：A 有缓存、游标、冲突和未同步草稿时退出并切换 B，B 无法读到 A 内容；A 的未提交内容不被静默销毁。

### A07 / P2：B04–B06 的 API 辅助函数取不到令牌，并把鉴权失败当空集合

- Q3 执行失败套件实际 helper，结果为 null。后端 authenticate 对缺 Bearer 返回 401。后续不检查状态，直接 `(body?.list ?? [])`，从而把错误响应变成“0 条”。uid 也可能在前置 auth/me 失败后为 undefined。

- 修复：共用正确的会话辅助函数，前置 auth/me 和所有核查请求必须显式断言状态/响应形状；记录精确项目、保存响应 ID；失败立即终止依赖场景。用正常执行人及具备目标项目权限的复核人。
- B05 注入按明确项目标识匹配，捕获原生 alert/dialog，不在 body 文本中搜索原生提示；去掉吞异常和强制点击掩盖前置失败的做法。
